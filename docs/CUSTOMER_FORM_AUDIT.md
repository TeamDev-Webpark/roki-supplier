# ผลตรวจโฟลและความครบถ้วนของฟอร์มใบเสนอราคา

ตรวจวันที่ 23 พฤศจิกายน 2026 · ขอบเขต: Interactive mockup ใน `design-demos` เทียบไฟล์ลูกค้าใน `docs`

## ข้อสรุป

อัปเดตหลังการตรวจ: หน้าคลังสูตรแยก Single Part และ Assembly ตามประเภทหลักแล้ว และการเพิ่ม master ต้องเลือกประเภทอย่างชัดเจนก่อนบันทึก คำขอแสดงชื่อฟอร์มจาก master การเปลี่ยนนี้แก้การจัดหมวดและการเลือกประเภทเท่านั้น ประเด็นเปอร์เซ็นต์ สูตรย่อย การปัดเศษ BOM และข้อมูลสเปกที่รายงานด้านล่างยังต้องดำเนินการต่อ

**ยังยืนยันว่าระบบตรงฟอร์มลูกค้าครบไม่ได้** โฟลหลักตรงกับคำสั่งล่าสุดของผู้ใช้ แต่ข้อมูลก่อนส่งคำขอ แบบฟอร์มย่อย กติกาคำนวณ และความครบถ้วนของเอกสารยังมีช่องว่างจริง โดยเฉพาะการส่งคำขอด้วยข้อมูลหัวเอกสารที่เดามา การแก้พารามิเตอร์สูตรโดย Supplier ความสัมพันธ์ราคาชิ้นส่วนย่อย และวันสิ้นสุดราคา

การมีหมวด A–E หรือหน้าพิมพ์คล้ายต้นฉบับ ยังไม่ใช่หลักฐานว่าสูตรและรายละเอียดถูกต้องครบถ้วน

ครั้งนี้อ่านต้นฉบับ ตรวจโค้ด และทดลองในเบราว์เซอร์แยกสำหรับตรวจสอบเท่านั้น ข้อมูลผู้ใช้งานในเบราว์เซอร์ที่เปิดใช้งานจริงไม่ถูกรีเซ็ตหรือเปลี่ยน และไฟล์ต้นฉบับลูกค้าไม่ถูกแก้ไข

ข้อควรตีความ: มีฟอร์มหลัก 2 กลุ่มคือ Single Part และ Assembly ส่วน Steel/Injection/Rubber เป็นลักษณะย่อยของฟอร์มและสูตร ไม่ได้หมายความว่าลูกค้าบังคับให้เพิ่มฟอร์มหลักประเภทที่ 3

## โฟล: สิ่งที่ตรงและสิ่งที่ต่างจากเอกสาร

โฟลปัจจุบันคือ WEBPARK Issue สร้าง/ส่งคำขอ → Supplier Issue กรอกต้นทุน → Supplier Approve ส่งกลับ → WEBPARK Check ตรวจ → WEBPARK Approve อนุมัติราคาซื้อ

| ประเด็น | ผลตรวจ |
|---|---|
| ส่งคำขอโดยไม่อนุมัติภายในก่อน | ตรงคำสั่งล่าสุดของผู้ใช้ ไม่ใช่ข้อผิดพลาดที่ควรย้อนกลับไปเพิ่มอนุมัติก่อนส่ง |
| ไม่มี WEBPARK Issue รับใบเสนอราคาแล้วอนุมัติซ้ำ | ตรงคำสั่งล่าสุด แต่ต่างจากประชุมหน้า 3–4 ที่ระบุ Issue / Check / Approve ภายในบริษัท ต้องบันทึกเป็นการเปลี่ยน requirement เพื่อให้ลูกค้ายืนยัน |
| Supplier ไม่มี E-sign | ตรงประชุมครั้งที่ 2 หน้า 4 ซึ่งให้ Supplier กรอกและยืนยัน/Approve เท่านั้น |
| ช่อง Supplier Checked by ใน XLS และ WEBPARK Issued by ในแบบกระดาษ | เอกสารเก่ามีช่องมากกว่าโฟลใหม่ ไม่ควรสร้างลายเซ็นย้อนหลังหรือเพิ่มขั้นตอนเอง ต้องตกลงรูปแบบเอกสารใหม่ว่าจะตัดช่อง ระบุ N/A หรือใช้ชื่อผู้จัดทำจากการส่งคำขอ |
| รอบ 1 / 3 เดือน | มีในระบบและตรงประชุมครั้งที่ 2 |
| หลายชิ้นส่วน Supplier เดียวกันในคำขอเดียว | ตรงคำสั่งล่าสุด และมีการตรวจบริษัททั้งตอนเลือก บันทึก และส่ง |
| ใบเสนอราคาหลายชิ้นส่วน | ขณะนี้เป็นคำขอรวมหลายชิ้นส่วน แต่ใบเสนอราคาและการอนุมัติยังเป็นรายชิ้นส่วน (`q.item`) ถ้าลูกค้าต้องการใบเสนอราคาฉบับเดียวที่มีหลายบรรทัดและอนุมัติครั้งเดียว ยังต้องออกแบบเอกสารแม่และลำดับการอนุมัติรวมเพิ่มเติม |

## Issue ต้องกรอกอะไรก่อนส่ง

**Issue ไม่ควรกรอกราคาต้นทุนแทน Supplier** หน้าที่คือกำหนดว่าให้เสนอรายการใด ใช้สเปก/แบบ/สูตรอะไร ส่งให้ใคร ภายใต้ปริมาณและช่วงเวลาใด ข้อมูลอ้างอิงจากรอบเดิมควรถูกสำเนาพร้อมเวอร์ชัน ไม่ใช่เดาค่าเพื่อให้ผ่านการบังคับกรอก

| ข้อมูล | เจ้าของข้อมูลที่เหมาะสม | ระบบปัจจุบัน | ช่องว่าง / แนวทาง |
|---|---|---|---|
| Supplier code / name | WEBPARK ดึงจาก Supplier master | มีและแยกบริษัทในการส่ง | ตรวจว่าผูก Item Code กับ Supplier ถูกตัว; คำขอต้องเก็บ snapshot |
| Part No. / Part Name / ประเภท | WEBPARK ดึงจากทะเบียน | มี | รักษา snapshot ของเอกสาร ไม่ให้ชื่อหรือสเปกเก่าเปลี่ยนตาม master |
| RTP / Material reference code | WEBPARK จาก master หรือเหตุผลยกเว้น | มีช่องใน master แต่เว้นว่างและส่งได้ | ไม่ควรบังคับทุกกรณี เพราะบางช่องต้นฉบับว่าง; ถ้ารายการนั้นต้องมี ให้บังคับหรือระบุเหตุผลว่าไม่มี |
| Drawing No. กับ Drawing Revision | WEBPARK ระบุแบบที่ร้องขอ | รวมเป็นช่องเดียว; ถ้าไม่มีระบบเติม `A01` | แยกเลขแบบ/Revision หรือกำหนดความหมายชัด; ไม่ใส่ revision สมมติเพื่อให้ผ่าน |
| ไฟล์ Drawing และเวอร์ชันสเปก | WEBPARK ส่งสเปกตั้งต้น; Supplier แนบหลักฐานเพิ่มเติม | Issue มี URL ไม่บังคับ; แนบรูป/PDF ได้เมื่อ Supplier กรอกใบเสนอราคา | ยังไม่มีไฟล์สเปกจาก Issue ที่ผูกกับคำขอและ frozen version; ไม่ควรพึ่ง URL ที่เปลี่ยนปลายทางได้เพียงอย่างเดียว |
| จำนวนผลิตอ้างอิง | WEBPARK กำหนดฐานการเสนอราคา | มีช่องจำนวน >0; เมื่อ master ไม่มีจำนวนจะเติม `1` | ต้องระบุจำนวนจริงหรือเลือกกรณีไม่มี forecast พร้อมเหตุผล ไม่เดา 1 |
| หน่วยช่วงเวลา Qty/Y / Qty/M / Qty/2Y | WEBPARK กำหนด | จำนวนไม่มี period ใน request spec; master ใช้ต่อปี แต่ Assembly formula ใช้ต่อเดือน | เสี่ยงเปลี่ยนความหมายของจำนวนเดิม ต้องแยกจำนวนและช่วงเวลาออกจากรอบทบทวน 1/3 เดือน |
| รูปแบบย่อย Injection / Rubber / Steel / Assy | WEBPARK เลือก template/profile | เลือกสูตรได้หลายชุด แต่เริ่มต้นมี standard และ assembly | ควรมี profile ที่ตรวจเทียบต้นฉบับแล้ว พร้อมช่องและหน่วยตามแต่ละชนิด |
| สูตรและเวอร์ชัน | WEBPARK Issue/Approve จัดการ; Issue เลือก | มีและตรึงเลขเวอร์ชันตอนส่ง | ยังต้องตรึง parameter ที่ WEBPARK เป็นผู้ควบคุมด้วย ไม่ใช่เฉพาะเลขเวอร์ชัน |
| BOM / ชิ้นส่วนย่อย / จำนวนใช้ | WEBPARK ระบุโครงสร้าง; Supplier ให้ราคาตามรายการ | master เก็บ `children` ได้ | ยังไม่นำ BOM ไปสร้างแถวใน blank form ของ Assy ใหม่ และยังไม่ผูกใบต้นทุนของลูกกับใบหลัก |
| รายละเอียดวัสดุ/น้ำหนัก/ขั้นตอนที่บริษัทควบคุม | WEBPARK ส่งสเปกอ้างอิง; Supplier เติมส่วนที่ได้รับมอบหมาย | รอบเดิมสำเนาบางค่าจากใบอนุมัติเก่า; รายการใหม่มีแถวว่าง | ขาดขั้นตรวจ/แก้โครงแบบตั้งต้นตามสเปกจริงก่อนส่ง; อย่าสับสนกับการให้ Issue กรอกราคา |
| Beginning | WEBPARK เสนอวันเริ่มใช้; Supplier ยืนยันตามนโยบาย | มี required date ก่อนส่ง | Supplier เปลี่ยนได้โดยไม่มีการเปรียบเทียบกับค่าที่ร้องขออย่างชัดเจน |
| Ending | WEBPARK กำหนดช่วงราคา | ไม่มี structured field | Assy มี Beginning และ Ending จริง; ต้องเก็บและนำไปตัดสิน Active / Expired |
| Review cadence / due review | WEBPARK | มี 1/3 เดือนและ snapshot รอบ | เป็นกำหนดทบทวน ไม่ใช่วันหมดอายุของราคา ต้องแยกจาก Ending |
| กำหนด Supplier ตอบ | WEBPARK Issue | มี required | ตรวจแล้วมีการบังคับไม่ให้วันตอบก่อนวันที่สร้าง |
| ชื่อคำขอ / เหตุผล / ข้อความถึง Supplier | WEBPARK Issue | มีและบังคับ | เหตุผลคำขอเป็นคนละเรื่องกับเหตุผลเปลี่ยนราคาที่ Supplier ต้องกรอก |
| สกุลเงิน / VAT / Payment terms | นโยบายบริษัทและข้อตกลง Supplier | ราคาคง THB และข้อความไม่รวม VAT; ข้อตกลงอื่นใส่ Remark ได้ | Assy มี Payment Term Credit 60 Days; ถ้าต้องใช้ตรวจ/ค้น/พิมพ์อย่างแน่นอนควรเป็นข้อมูลแยกหรือ template note ที่ตรึงไว้ |

## ผลทดลองที่ยืนยันช่องว่างจริง

ใช้ `design-demos/audit-customer-forms.cjs` เปิด context แยก มีข้อมูลทดลองเฉพาะใน context นั้น ผลเต็มอยู่ที่ `design-demos/previews/customer-form-audit-evidence.json`

### A. ส่งคำขอใหม่ด้วยหัวเอกสารที่ข้อมูลต้นทางยังไม่ครบได้

สร้างชิ้นส่วนใหม่ ใส่เพียงรหัส ชื่อ Supplier และใช้ประเภทเริ่มต้น โดยไม่กรอก RTP, Drawing หรือปริมาณใน master:

- ฟอร์มสร้างคำขอเติมปริมาณ `1` และ Drawing `A01` ให้อัตโนมัติ
- RTP ยังคงว่าง
- ไม่มีช่องอัปโหลดไฟล์ใน dialog ของ Issue
- เมื่อกรอกเหตุผล ระบบยอมส่งคำขอได้

ผลคือ required validation ผ่าน แต่ไม่ได้พิสูจน์ว่ารายละเอียดสำหรับเสนอราคาถูกต้องจริง ปัญหาไม่ได้อยู่ที่ Issue ยังไม่ได้ใส่ราคา

หลักฐานโค้ด: `catalog.js:partDialog/savePart`, `sourcing.js:requestFormRows/readRequestSpecs`, `request-approval.js:rfqDraftDialog/rfqSave`

### B. เลขเวอร์ชันสูตรตรึงแล้ว แต่ Supplier ยังเปลี่ยนพารามิเตอร์ราคาได้

ค่าเริ่มต้นของสูตรให้ `profit.lock=false`, `spare.lock=false` และ adjustment ต่าง ๆ ไม่ล็อก จึงแก้กำไร ฐานกำไร และเปอร์เซ็นต์ได้จาก Supplier editor

ทดลองส่งใบเสนอราคาจริงใน context ตรวจสอบ โดยยังใช้ formula version 1 แต่เปลี่ยนกำไรเป็น **99%** ระบบรับเป็น `Supplier approval` ได้ พร้อมเปลี่ยนปริมาณจากที่ร้องขอเป็น 999, Drawing เป็น `SUPPLIER-CHANGED` และวันเริ่มใช้เป็น `2020-01-01`

นี่ไม่ได้หมายความว่า Supplier เปลี่ยน expression หรือเลขเวอร์ชันสูตรได้ แต่แสดงว่า “เลือกเวอร์ชันแล้ว” ยังไม่เพียงพอให้พารามิเตอร์ทั้งหมดเป็นกติกาที่บริษัทควบคุม ต้องกำหนดว่าเปอร์เซ็นต์/ปริมาณ/แบบ/วันที่ใดล็อก ใดแก้เสนอได้ และถ้าแก้ต้องแสดงส่วนต่างจากคำขอให้ Check ตรวจ

หลักฐานโค้ด: `quote-model.js:defaultFormats`, `workspace.js:costSummary/costRowsUI/editor/saveQuote`

### C. BOM ใหม่ไม่ได้กลายเป็นแบบฟอร์มองค์ประกอบ

สร้างข้อมูล Assembly ใหม่ที่มีลูก 2 รายการ ปริมาณใช้ 2 และ 1 แล้วเรียกสร้าง blank form: ได้แถว component ว่างเพียง 1 แถว ปริมาณ 1 ไม่มีรหัสลูกทั้งสอง

ข้อมูล `children` ปัจจุบันจึงเป็นข้อมูลแสดงประกอบ ไม่ใช่ BOM ที่ใช้ขับเคลื่อนแบบฟอร์มราคาอย่างครบถ้วน

หลักฐานโค้ด: `sourcing.js:blankRequestCosts`, `catalog.js:childrenHtml/parseChildList`

### D. ผลคำนวณไม่ตรง Excel ทุกกรณี

ป้อนข้อมูล `single part -Inj` ฝั่งต้นฉบับให้เครื่องคำนวณปัจจุบัน:

| วิธี | ผลรวมบาท/ชิ้น |
|---|---:|
| ใช้ค่าเริ่มต้นปัจจุบันของ standard formula | 56.97 |
| เปลี่ยน Component loss เป็น 3% และ Spare part cost เป็น 15% ให้ตรงชีต | 62.20 |
| สูตร Excel ต้นฉบับ `I67=I64+I65+K66` มีค่า 62.20839000000001 และแสดง 2 ตำแหน่ง | 62.21 |

สาเหตุที่ต้องแยกกันแก้: ค่าพารามิเตอร์เริ่มต้นยังไม่ตรง profile และระบบปัดหมวดเป็น 2 ตำแหน่ง/ตัดกำไรกับ spare ก่อนรวม ขณะที่สูตรที่อ่านใน Excel นี้รวมค่าที่ไม่ถูก ROUND ในเซลล์เหล่านั้น ต้องกำหนดกติกาปัดเศษกับลูกค้าและใช้ชุดตัวอย่างยืนยัน ห้ามใช้เพียงความใกล้เคียงของตัวเลขเป็นเกณฑ์ผ่าน

ค่า default 56.97 เป็นผลทดลองของข้อมูลชุดเดียวกันกับสูตรเริ่มต้น ไม่ใช่การกล่าวว่าใบ mockup ที่มีอยู่ทุกใบแสดงยอดนี้ เพราะใบเก่าแต่ละใบมีเปอร์เซ็นต์ของตนเอง

## เอกสารพิมพ์และวงจรอายุราคา

- มี Original / Revised, เหตุผล, ค่า Beginning และหลักฐานการทำงาน แสดงได้ในภาพรวม
- ยังไม่มี Ending ดังนั้น `activeQuote()` เลือกราคาที่อนุมัติและ effective≤วันนี้ โดยไม่ตรวจวันหมดอายุ ราคาอาจยังแสดง Active หลังวันสิ้นสุดที่มีในฟอร์มลูกค้า
- หัวคอลัมน์หน้าพิมพ์ตัดข้อความหลังเว้นวรรคตัวแรก เช่น label ที่มีหน่วยหรือคำอธิบายหลายคำ อาจเหลือเพียง Part / Cost / Material ทำให้ความหมายกับหน่วยไม่ครบเท่าฟอร์มต้นฉบับ (`workspace.js:formColumn`)
- ส่วนหัวบริษัทหน้าพิมพ์ยังเป็นชื่อและข้อความ workspace ไม่ใช่ letterhead ที่อยู่/โทรศัพท์/รหัสแบบฟอร์ม/Revision เอกสารตามต้นฉบับ การใช้ชื่อ WEBPARK เป็นการเปลี่ยนแบรนด์ตามคำสั่งผู้ใช้ ไม่ใช่ข้อผิดพลาดที่ต้องเปลี่ยนกลับเป็น ROKI
- ช่องลงนามใหม่มี Supplier 2 ขั้นและ WEBPARK 2 ขั้นตามโฟลปัจจุบัน ขณะที่ต้นฉบับบางฉบับมี 3 ช่องต่อฝั่ง ต้องออกแบบ template ใหม่ที่อธิบายความต่างได้ ไม่ใส่ลายเซ็นแทนขั้นที่ไม่เกิด
- รูป/PDF ของ Supplier แยกชนิดและจำกัดจำนวนแล้ว; สิ่งที่ยังขาดคือไฟล์สเปกจาก WEBPARK ณ เวลาส่งคำขอ และการยืนยันว่าไฟล์ใดคือแบบที่ใช้คำนวณ
